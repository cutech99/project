# 예약 Oracle SQL 시연 가이드

역할 안내와 현재 구현 현황은 [상위 README](../README.md)에서 확인한다. 모든 변경은 `feature/reservation`의 담당 폴더 안에 한정했다. 공용 DB에 적용하지 않는다. SQL*Plus, SQLcl 또는 SQL Developer **스크립트 실행(F5)** 기준이며 UTF-8, 자동 COMMIT OFF를 사용한다. 비밀번호는 저장/명령 인자에 기록하지 않고 접속 도구의 입력창에서 입력한다.

## 파일과 실행 순서

아래 경로는 `roles/02-reservation` 기준이다. 해당 폴더에서 SQL 클라이언트를 시작하고 `@sql/파일명.sql`로 실행한다. 모든 스크립트를 일괄 실행하지 않는다.

1. `sql/00_inspect.sql`: 개인 DB의 컬럼, PK/FK/CHECK, 상태, 시퀀스 확인. 빈 DB면 첫 조회 중 예약/레인 조회의 ORA-00942가 예상된다.
2. 둘 중 하나 선택:
   - **1번 테이블이 이미 존재**: `sql/02_alter_existing.sql` → 기존 예약의 시작/종료/인원을 확인하여 수동 보완·COMMIT → `sql/03_validate_existing.sql`.
   - **예약 테이블 두 개 모두 없음**: 1번과 동일한 MEMBER/LANE 부모 테이블을 개인 DB에 준비 → `sql/01_create_empty.sql`. 이것으로 NOT NULL까지 완료되므로 02/03은 실행하지 않는다. USAGE도 1번 정의가 있어야 취소 프로시저가 컴파일된다.
3. `sql/04_transaction_api.sql`: 신규 생성/취소 프로시저. `SHOW ERRORS` 및 USER_ERRORS 검사. 같은 이름의 프로시저가 있으면 재실행하지 말고 내용 비교한다.
4. DDL 완료 후 새 **시연 전용 세션**을 열고 `sql/05_dummy_data.sql`: 가상 회원1, 레인4, 6명 예약1/배정2. COMMIT 없이 같은 세션에서 다음 단계 진행.
5. `sql/06_select_join.sql`, `sql/07_overlap_check.sql`: 조회/용량/중복 확인.
6. `sql/10_tests.sql`: 예상 코드/행 수를 자체 검사, 성공 시 PASS와 ALL PASS. 테스트 자체의 변경은 저장점으로 되돌려 05 더미만 유지.
7. 선택 시연: `sql/08_create_example.sql` → `sql/09_cancel_example.sql` → 조회. 둘은 `new_reservation_id` 바인드를 공유하므로 같은 세션에서 실행한다.
8. 기본 마무리: `ROLLBACK;` → 05 이후 미커밋 회원·레인·예약·배정을 되돌림. 개인 DB에 시연 데이터 보관이 필요할 때만 직접 COMMIT을 선택. 프로시저가 호출자 트랜잭션을 확정하지는 않는다.

DDL에는 암묵적 COMMIT이 있으므로 05 이후 CREATE/ALTER를 실행하지 않는다. 오류 종료 설정은 SQL*Plus에서 세션을 종료하고 미커밋 작업 전체를 롤백할 수 있다. 별도 시연 세션만 사용한다. DDL 중간 실패는 앞선 DDL을 되돌리지 못하므로 00으로 현재 상태를 확인하고 실패 지점부터 수동 검토한다. DROP/DELETE 초기화는 제공하지 않는다. 롤백에도 시퀀스 NEXTVAL은 복원되지 않으며 번호 공백은 정상이다.

## 예상 테스트 결과 (아직 Oracle 미실행)

| 시나리오 | 기대 |
|---|---|
| 정상 예약, 회원·레인 JOIN | 6명 예약에 배정2행, 요약 조회1행 |
| 6명 레인1개 | ORA-20014, 예약 증가 없음 |
| 같은 레인 11~12시 | 기존10~12시와 충돌 ORA-20017 |
| 12~14시 | 경계 맞닿음 허용, 정확히2시간 성공 |
| 취소 후10~12시 재사용 | 취소 연결행2개 보존, 신규 예약 성공 |
| 인원0/소수 직접 INSERT | ORA-02290 |
| 2시간 초과 직접 INSERT | ORA-02290 |
| 시작시간 NULL | ORA-01400 (03 적용 완료 전에는 보장 안 됨) |
| API의 0시간/역전/3시간 | ORA-20010 |
| 같은 예약-레인 직접 중복 INSERT | ORA-00001 |
| 없는 회원 / 없는 레인 직접 참조 | ORA-02291 |
| 첫 배정 후 둘째 배정 FK 오류 강제 주입 | 헤더/첫 배정 모두 저장점으로 롤백 |
| 점검/사용불가 시설 | ORA-20015 |

프로시저는 없는 레인을 사전조회하므로 그 경로에서는 ORA-01403이 날 수 있다. FK 자체 검증은 직접 INSERT 테스트로 분리했다. 배정 도중 오류 테스트는 익명 블록으로 실제 DML 중간에 FK 오류를 강제하며, 생성 프로시저는 모든 레인을 먼저 검증한다. 둘을 같은 테스트라고 주장하지 않는다.

## 두 세션 동시성 검증 (수동, 미실행)

1. 별도 개인 시험 DB에서 05 더미만 COMMIT하여 두 세션에 보이게 한다. 10 테스트는 이 두 세션 실험과 분리한다. 2030-01-17에는 기존 예약이 없는지 확인한다.
2. 세션 A: 아래 코드를 실행하고 COMMIT하지 않는다.

```sql
VARIABLE rid NUMBER
EXEC R2_CREATE_RESERVATION(-92001,DATE '2030-01-17',DATE '2030-01-17'+1/24,1,SYS.ODCINUMBERLIST(-92001),:rid);
```

3. 세션 B: 같은 코드를 실행. A가 레인 행을 보유하므로 대기해야 한다.
4. A에서 COMMIT하면 B는 깨어난 뒤 별도 SELECT로 최신 예약을 읽고 ORA-20017이어야 한다. 양쪽 조회 후 B는 ROLLBACK한다.
5. 다른 빈 시간대로 반복하고 이번에는 A에서 ROLLBACK. B는 성공해야 하며 B도 ROLLBACK하여 신규 예약을 남기지 않는다.
6. 여러 레인의 입력 순서를 뒤집어도 API 내부 오름차순 잠금인지 검증한다. 레인 시설 상태 변경 경로와의 경쟁은 3번과 규약 통합 후 별도 검증한다.

## 실제 검증 기록

현재 환경에는 sqlplus/SQLcl 실행 파일이 확인되지 않았고 Oracle 접속 정보도 사용하지 않았다. Oracle DDL/PLSQL 컴파일, INSERT, 오류 코드, 잠금/동시성은 **모두 미검증**이다. 파일 목록·변경 범위·원본과 컬럼명·제약/트랜잭션 흐름을 정적으로 점검했다. H2 실행은 Oracle 검증을 대체하지 않으므로 수행하지 않았다. 발표 시 PASS 출력은 개인 Oracle에서 실제 실행한 뒤에만 성공 증빙으로 사용한다.

## 팀 회의에서 합의할 것

- 현행 호환안과 목표안 중 통합 기준, RES_DATE 의미, 기존 행의 종료시간/인원 보완 책임.
- STATUS vs RESERVATION_STATUS 및 영어/한글 상태 도메인, 예약대기 점유 여부.
- LANE_NO/STATUS vs LANE_NUMBER/LANE_STATUS, 회원 컬럼 차이, USAGE 구조/시퀀스 이행 담당.
- 이용 시작 이후 취소 정책, 다중 레인 일부 이용 시 예약 상태 소유권.
- 레인→예약→이용 잠금 순서, 배정/시간/인원 변경 허용 여부와 모든 쓰기 경로의 준수.
- DATE(초 단위) vs TIMESTAMP, 앱/DB 표시 시간대(제안 Asia/Seoul), 최대 인원/예약 가능 시간대/과거 예약 정책.
- 공통 Spring Boot 패키지/예외 처리/ID 정책, 개인 DB 통합 시험 일정.

## Spring Boot 구현 순서

1. 위 스키마·상태·시간대 계약 확정, 1번 JDBC 환경/시퀀스에 연결.
2. 예약 DTO와 Repository 조회/JOIN, 회원·시설 선택 목록.
3. Service `@Transactional`: 인원/시간/레인 검증 → 정렬 잠금 → 최신 상태/중복 재검사 → 예약/배정 INSERT. DB 프로시저 호출 또는 Java 구현 중 한 가지를 기준으로 통일.
4. 생성/조회 Controller와 Thymeleaf 폼, 오류 코드별 사용자 메시지.
5. 취소 Service의 동일 잠금과 이용 상태 검사, 취소 화면.
6. Oracle 통합 테스트에서 경계시간·FK·중간실패 롤백·두 연결 동시 예약 검증.
7. 3번의 이용 시작/종료 상태 동기화 연결 → 4번 통계/UI 연결 → 개인 DB 시연 및 승인 후 커밋·푸시.
